# Email campaign landing pages (written 28 Aug 2026)

The plan for `/go/<campaign>/` — dedicated entry pages for the Sender sends, and
the vehicle for narrowing down a visual direction ahead of any 2027 redesign.

Context: `HOLIDAY-PLAN.md` Engine 4 (the ~2,000-person Sender list is the biggest
lever between now and Christmas) and Engine 3 (the AOV work those sends will land
on). Read those first.

---

## Why campaigns get their own pages at all

Today a send would have to point at `trivia-store.html` or a product page. Both
are built for a stranger arriving from Google — full nav, dropdowns, price
ladder, 700 words of "what is music bingo". Someone who opened an email about
Halloween has already decided; every one of those elements is a way to leave.

A campaign page is one offer, one price, one button, no nav dropdowns. It also
gives each send a **known denominator** — emails delivered → landing page
sessions → `begin_checkout` — which is the first time anything on this site has
been measurable end to end.

---

## Shape

```
/go/halloween/       late Sept send
/go/christmas/       mid Oct send
/go/bundles/         early Nov send
/go/last-minute/     early Dec send
```

Rules, all non-negotiable and all learned the hard way here:

- **Trailing slash**, as every directory page on this site (see CLAUDE.md,
  "URL shape"). Run `canonicalize-trailing-slash.js` after generating.
- **`noindex,follow`, and NOT in `sitemap.xml`.** These pages restate product
  copy and would compete with the store in search. This site spent Jul–Aug 2026
  digging out of exactly that hole; do not reopen it.
- **Prices read from the product pages** at build time, like
  `add-cross-sell.js` / `add-price-ladder.js` / `build-song-library.js`. Never
  typed. Campaign pages go on the re-run-after-repricing list.
- Generated by a tool from a small JSON spec (`_content/campaigns.json`), same
  idiom as the song library — edit the data, never the generated HTML.
- Every buy button keeps `class="ls-buy" data-product="pNN"` so
  `bake-buy-links.js` and the tracking both work unchanged.

## What goes on one

Six blocks, in this order, and nothing else:

1. **One sentence naming the occasion**, not the company. "Your Halloween night,
   sorted." The reader already knows who we are — they opened the email.
2. **The offer, with the arithmetic.** The same honest maths the cross-sells now
   use: *"The Halloween pack is $10.99. The Holidays 6-Pack is $46.99 — which
   puts the other five at $7.20 each."*
3. **Three products maximum.** One obvious pick, one upgrade, one stretch.
   More than three is a decision, and a decision is a bounce.
4. **What's in the box** — 250 randomized cards, printable callsheet, ready-made
   playlists. Three lines.
5. **The song list link.** Fifty pages of proof the games are real, free to
   read. This is the one piece of the site nobody else has.
6. **The same CTA again.** No footer nav, no dropdowns, no blog links.

## Testing a direction — what's honest about it

**This is not an A/B test and should never be reported as one.** At ~2,000
recipients per send, splitting the list gives arms of 1,000, and at a realistic
3–5% click rate that's 30–50 landing-page sessions per arm. Nothing about a
30-session arm is significant. The maths is in the previous session's analysis:
proving even a 100% conversion lift needs ~780 sessions per arm.

What it *is*: **one direction per send, four sends, judged directionally**, with
the same instrumentation on each so the comparison is at least like-for-like.
That's qualitative evidence for a design decision — which is the right weight of
evidence for a design decision at this traffic.

Two things make it much less useless than it sounds:

- **The offer changes between sends and the design changes with it, so they're
  confounded.** Accept that and don't over-read a single number. What you're
  looking for is a direction that's *clearly* worse or *clearly* better, not a
  10% difference.
- **Microsoft Clarity** (free, no traffic minimum) on the campaign pages. 40
  session recordings tells you more about a layout than 40 conversions ever
  will — where they stop scrolling, what they hover, what they never reach.
  Install it before the first send, not after.

### The three directions

| # | direction | what it tests |
|---|---|---|
| A | **Current, tightened.** Today's theme, single column, nav stripped, one CTA. | The control. How much of the problem is layout rather than looks. |
| B | **Chalkboard.** The Aug 2026 prototype — mahogany/brass, chalk hero, bingo-ticket product cards. | Whether a strong, specific identity converts better than a neutral one. |
| C | **Plain and fast.** Near-zero chrome. Big type, a three-item list, no imagery, loads instantly. | The honest control for "does the look matter at all". Often wins. |

Run A first (late Sept, Halloween) so there's a baseline before anything is
judged. Then B (Christmas), then C (bundles). December repeats whichever is
ahead — that send is the year's biggest and isn't the place to experiment.

**If B doesn't clearly beat A and C, that is the answer**, and the 2027 redesign
budget goes to something else. That's the outcome this is designed to be able to
return, and it's a real possibility.

### Corrections to carry into direction B

From the prototype as supplied — these are wrong in it and must not ship:

- Prices were $29 / $49 / $199 against real prices of $10.99 / $27.00 / $415.50.
  Read them from the pages.
- The headline **"Fill the room. Not a subscription."** argues against the
  business: there are two subscription products and ~41 subscribers, and
  `HOLIDAY-PLAN.md` calls subscriptions the only revenue that persists past
  December. The site title tag has the same problem ("No Monthly Fees").
- Four type families, with 92px handwriting as the H1.
- "New releases added free, forever" — the Gold Club page says a 1-year Bingo
  Card Generator licence. Check any claim like this against the product page.

## Measurement, and what each send should record

The tracking shipped 28 Aug (`assets/js/track.js`) already fires
`begin_checkout` with an `origin` on every buy click. Two build-time additions:

- `track.js` `ORIGINS` gains a campaign rule so clicks report
  `origin: "campaign-halloween"` rather than the `"page"` fallback.
- Every link in the email carries UTMs —
  `?utm_source=sender&utm_medium=email&utm_campaign=halloween-2026` — so GA4
  attributes the session even before the click.

Record per send, in this doc, as they happen:

| send | direction | delivered | opens | clicks | sessions | begin_checkout | orders |
|---|---|---|---|---|---|---|---|
| Halloween, late Sept | A | | | | | | |
| Christmas, mid Oct | B | | | | | | |
| Bundles, early Nov | C | | | | | | |
| Last-minute, early Dec | winner | | | | | | |

**Orders is the column that can't be filled from the site.** LemonSqueezy
checkout is off-domain; the number has to come from the LS dashboard, matched by
date. Enabling LemonSqueezy's Google Analytics integration against
`G-LYMVV05F3X` closes that gap permanently and is worth doing before the first
send.

### What `/go/halloween/` actually is

9KB against a 39KB product page. One occasion, three rungs
($10.99 → $32.99 → $46.99), the full song list as free proof, no nav dropdowns,
no blog links, no footer maze. Buy buttons keep `ls-buy` + `data-product` so the
promo-code prefill, `bake-buy-links.js` and the tracking all work unchanged.

Adding the next campaign is an entry in `_content/campaigns.json` and a re-run.
